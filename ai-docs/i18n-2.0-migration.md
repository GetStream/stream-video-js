# i18n changes in 2.0

Four breaking changes, all in 2.0:

1. **Translation keys are namespaced identifiers**, not the English text.
   `t('Mute all')` became `t('participantList.muteAll.label', 'Mute all')`.
2. **There is no bundled `en.json`**, and neither SDK exports `translations` any
   more. The English copy lives inline at each `t()` call site.
   `yarn i18n:export` writes a translator-facing JSON on demand.
3. **`<StreamVideo translationsOverrides>` is now `<StreamVideo translations>`,
   and the semantics invert.** The old prop _replaced_ the SDK's dictionary; the
   new one _registers over_ it. Partial dictionaries are now safe.
4. **`fallbackLanguage` is removed**, along with `StreamI18n`,
   `StreamI18nProvider` and the types around them. The runtime moved to
   `@stream-io/i18n`, shared with the React Native SDK and with Stream Chat, and
   is re-exported from both video SDKs as `Streami18n`.

One thing got better rather than broke: **11 strings became translatable for the
first time.** The eight `CallingState` labels and the three call-stats verdicts
used to be resolved from a runtime value, and five of them had no catalog entry
at all, so no dictionary could reach them. They are literal `t()` calls now.

Everything below applies to `@stream-io/video-react-sdk` and
`@stream-io/video-react-native-sdk` alike; where they differ, it says so.

## Do I need to do anything?

| If you…                                                           | Action                                                                                        |
| ----------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| use the SDK in English and never touched i18n                     | **Nothing.**                                                                                  |
| passed `translationsOverrides` to `<StreamVideo>`                 | Rename the prop to `translations`, and rename your keys — see below                           |
| called `registerTranslation()`                                    | Construct `Streami18n` instead of `StreamI18n`, and rename your keys                          |
| imported `translations` / `translations.en` from the SDK          | Removed. Delete the import — see [The `translations` prop](#the-translations-prop)            |
| passed `fallbackLanguage`                                         | Removed. Delete it — see [`fallbackLanguage` is gone](#fallbacklanguage-is-gone)              |
| call `t()` in your own components                                 | Import path is unchanged, but `useI18n()` no longer returns `i18n` and `t` is now key-checked |
| imported `StreamI18n`, `StreamI18nProvider`, `TranslationsMap`, … | Removed — see [Removed exports](#removed-exports)                                             |
| passed only `client`, `language` or `i18nInstance`                | **Nothing** — those props are unchanged                                                       |

## Renaming your keys

**Renaming is not optional and it fails quietly.** An old key never matches, so
your override silently stops applying and the SDK's English renders instead — no
error, no warning, nothing in the console. Every override you carry forward has
to be renamed, or it is dead weight that looks like it works.

Almost every old key maps to exactly one new key. The full mapping — 169 rows
for the React SDK, 28 for React Native — is
[`i18n-2.0-key-map.json`](./i18n-2.0-key-map.json).

Before:

```tsx
<StreamVideo
  client={client}
  language="de"
  translationsOverrides={{
    de: {
      'Mute all': 'Alle stummschalten',
      Leave: 'Verlassen',
      'Rate {{ count }} star_one': '{{ count }} Stern bewerten',
      'Rate {{ count }} star_other': '{{ count }} Sterne bewerten',
    },
  }}
/>
```

After:

```tsx
import type { TranslationDictionary } from '@stream-io/video-react-sdk';

const de: TranslationDictionary = {
  'participantList.muteAll.label': 'Alle stummschalten',
  'callControls.cancelCallButton.leaveCall.title': 'Anruf verlassen',
  'callFeedback.starRating.rateStars.ariaLabel_one':
    '{{ count }} Stern bewerten',
  'callFeedback.starRating.rateStars.ariaLabel_other':
    '{{ count }} Sterne bewerten',
};

<StreamVideo client={client} language="de" translations={{ de }} />;
```

Typing the dictionary as `TranslationDictionary` turns the silent failure into a
compile error, which is the whole point of doing it that way:

```ts
const de: TranslationDictionary = {
  'participantList.muteAll.label': 'Alle stummschalten',
  'Mute all': 'Alle stummschalten', // ← 1.x key: compile error, exactly what you want
};
```

Plurals live in the dictionary as `<key>_one` / `<key>_other`; the call site uses
the bare `<key>` and passes `count`. Languages that need `_few`, `_many` or
`_zero` can add them — `TranslationDictionary` accepts every category
`Intl.PluralRules` can select.

> Do **not** key a dictionary on `Partial<Record<TranslationKey, string>>`.
> `TranslationKey` is the set `t()` accepts, where a plural appears as the bare
> key; a dictionary needs the `_one` / `_other` entries, which that type rejects.
> `TranslationDictionary` already handles this.

### The rows that need a human

Most rows are a straight rename. Five are not:

- **`split`** — one old key became two whole sentences. Both cases are the
  `{{ direction }}` pattern in the participant actions menu:
  `'{{ direction }} fullscreen'` becomes
  `participantView.actionsMenu.enterFullscreen.label` /
  `…leaveFullscreen.label`, and `'{{ direction }} picture-in-picture'` becomes
  `…enterPip.label` / `…leavePip.label`. If you translated those, translate both
  new keys and delete the old one.
- **`mergedInto`** — one React Native row. The old singular sentence,
  `There is {{numberOfParticipants}} more person in the call.`, was absorbed as
  the `_one` form of `lobby.footer.otherParticipants.text`. It has no key of its
  own; supply the plural pair instead.
- **The `Enter` / `Leave` fragments** — sentence fragments that only ever filled
  the `{{ direction }}` slot. They have no replacement. Delete them.

Rows also carry a `note` where the call site changed shape (a plural that could
not select, an interpolation variable that was renamed). Read the note before
translating that row.

## Doing the rename

There is no codemod. The rename is mechanical enough to script against the
published key map, and the map is structured for exactly that — but the parts
that are _not_ mechanical are the parts that matter, so work through them
deliberately:

1. **Dictionaries.** For each entry, look the old English key up in
   `keys` for your platform and replace it with the row's `key`. Plural entries
   keep their `_one` / `_other` suffix on the new key. Leave anything the map
   does not mention: it is either your own copy or a key that no longer exists.
2. **Your own `t()` call sites.** `t('Old English')` becomes
   `t('namespace.component.thing.label', 'Old English')` — the second argument is the inline
   default, and it is what makes a missing dictionary entry render English
   rather than a raw key.
3. **Then compile.** If you typed your dictionaries as `TranslationDictionary`,
   the compiler finds every key you missed. That is the point of the type.

The cases a script cannot finish for you, all flagged in the map:

- **`split` rows and the `Enter` / `Leave` fragments** need the manual edits
  described above. There is no single new key to rewrite to.
- **Non-literal keys** — `t(someVariable)`, a key built by template literal, or
  one read out of a config object — cannot be matched against the map at all.
  Find them with a grep for `t(` followed by something other than a quote.
- **Plural pairs whose call site changed** (the rows carrying a `note`) need the
  call site edited too, not just the key renamed.

## The `translations` prop

`<StreamVideo translationsOverrides>` is now `<StreamVideo translations>`, and it
does the opposite thing.

In 1.x the prop was handed to i18next as the whole resource bundle. Passing it
**replaced** the SDK's own dictionary rather than merging with it, so an
integrator supplying one German string dropped all 147 of the SDK's English
ones. That is why every sample app had to spread `sdkTranslations.en` back in by
hand — a workaround for a bug, not a pattern to copy.

In 2.0 the dictionaries are registered on the `Streami18n` instance, layered over
the SDK's bundled defaults. A partial dictionary is safe: a key you leave out
renders the English copy that ships inline at its call site, never a raw dotted
path.

Here is the real diff from `react-dogfood`, which is the change most affected
apps have to make. Before:

```ts
import de from './de.json';
import en from './en.json';
import es from './es.json';

import { translations as sdkTranslations } from '@stream-io/video-react-sdk';

export const appTranslations = { de, en: { ...sdkTranslations.en, ...en }, es };
export default appTranslations;
```

After:

```ts
import type { LooseTranslationDictionary } from '@stream-io/video-react-sdk';

import { runtimeDefaults } from '../i18n/runtimeDefaults';

import appDe from './app/de.json';
import appEs from './app/es.json';
import sdkDe from './sdk/de.json';
import sdkEs from './sdk/es.json';

export const appTranslations: Record<string, LooseTranslationDictionary> = {
  en: { ...runtimeDefaults },
  de: { ...runtimeDefaults, ...sdkDe, ...appDe },
  es: { ...runtimeDefaults, ...sdkEs, ...appEs },
};

export default appTranslations;
```

Four things changed:

- **The `sdkTranslations.en` spread is gone**, and so is the `en` dictionary it
  fed. There is no `translations` export to spread, and English no longer needs
  one — it comes from the call sites.
- **The dictionaries are split by owner.** `sdk/` holds keys from the SDK's
  catalog, `app/` holds the app's own. That split is what lets `sdk/*.json` be
  type-checked against `TranslationDictionary` while `app/*.json` is not.
- **`LooseTranslationDictionary`** types the combined value, because it carries
  app-owned keys alongside SDK ones.
- **`runtimeDefaults` goes under every language.** This app has one block of
  keys built from a runtime value (`language.*` in the transcription settings),
  which therefore carry no inline default. With `fallbackLng` off, a language
  whose dictionary omits them would render the raw dotted key. Most apps have no
  such keys and need none of this.

And at the call site:

```diff
 <StreamVideo
   client={client}
   language={language}
-  fallbackLanguage={fallbackLanguage}
-  translationsOverrides={appTranslations}
+  translations={appTranslations}
 >
```

`translations` is `Record<string, LooseTranslationDictionary>`, keyed by language
code, exactly as `translationsOverrides` was.

### `fallbackLanguage` is gone

The fallback is now each call site's inline English, which cannot be forgotten
and cannot go stale. `fallbackLng` is `false` in the shared runtime, and there is
no prop to change it.

If you genuinely want a second-language chain — Swiss German falling back to
German, say, rather than to English — set it on the instance:

```ts
const i18n = new Streami18n({
  language: 'de-CH',
  i18nextConfigOverrides: { fallbackLng: 'de' },
});
```

Note that `fallbackLanguage` never did the job people expected of it. In
`react-dogfood` it was set to catch `window.navigator.language` returning
`en-US` where the dictionaries were keyed `en`; the fix is to normalize the tag
before handing it to `<StreamVideo language>`, which is what that app does now.

### Removed exports

All of these came from `@stream-io/video-react-bindings` and were re-exported by
both SDKs. They are gone:

| Removed                                                               | Replacement                                                   |
| --------------------------------------------------------------------- | ------------------------------------------------------------- |
| `StreamI18n`                                                          | `Streami18n` — a different class, different options           |
| `StreamI18nConstructor`                                               | `Streami18nOptions`                                           |
| `StreamI18nProvider`                                                  | None. `<StreamVideo>` mounts the translation context itself   |
| `StreamI18nProviderProps`                                             | `UseStreami18nParams`                                         |
| `defaultTranslationFunction`                                          | None. The default `t` honours each call site's inline English |
| `TranslationLanguage`                                                 | `string`. Any code you register a dictionary for is valid     |
| `TranslationsMap`                                                     | `Record<string, LooseTranslationDictionary>`                  |
| `TranslationSheet`, `TranslationsForLanguage`, `TranslationsRegistry` | `TranslationDictionary` / `LooseTranslationDictionary`        |
| `TranslatorFunction`                                                  | `StreamTFunction` (key-checked) or `LooseTranslateFunction`   |
| `translations`                                                        | None. There is no bundled dictionary to import                |

`useI18n` keeps its name and its import path. Its shape changed:

```ts
// 1.x
const { t, i18n } = useI18n();

// 2.0
const { t, tDateTimeParser } = useI18n();
```

The `i18n` field is gone. If you were reaching through it to change language,
hold your own `Streami18n` instance and pass it as `i18nInstance`, or drive
`<StreamVideo language>` from state.

## Adding a language

```ts
import 'dayjs/locale/de';
import { Streami18n } from '@stream-io/video-react-sdk';
import type { TranslationDictionary } from '@stream-io/video-react-sdk';

const de: TranslationDictionary = {
  'participantList.muteAll.label': 'Alle stummschalten',
};

const i18n = new Streami18n({ language: 'de' });
i18n.registerTranslation('de', de);

<StreamVideo client={client} i18nInstance={i18n} />;
```

Or, without holding an instance, hand the dictionaries to `<StreamVideo>` and let
it construct one:

```tsx
<StreamVideo client={client} language="de" translations={{ de }} />
```

Both paths register over the SDK's defaults. Use the instance when you need the
options below; use the prop when you do not.

**Dates need the dayjs locale imported.** Only `en` is bundled. Without the
import, dates render with the English locale and the runtime logs a warning
naming the exact import you are missing.

**Relative dates need a `calendar` config on top of that.** No dayjs locale file
defines `calendar` — that field belongs to the calendar plugin — so a language
whose "today" / "yesterday" wording must read natively supplies it, either as a
constructor option or as the third argument to `registerTranslation`:

```ts
import 'dayjs/locale/de';

const i18n = new Streami18n({
  language: 'de',
  dayjsLocaleConfigForLanguage: {
    calendar: {
      sameDay: '[heute um] LT',
      lastDay: '[gestern um] LT',
      lastWeek: '[letzten] dddd [um] LT',
      nextDay: '[morgen um] LT',
      nextWeek: 'dddd [um] LT',
      sameElse: 'L',
    },
  },
});

// or, per language:
i18n.registerTranslation('de', de, { calendar: { sameDay: '[heute um] LT' } });
```

### React Native: `intl-pluralrules`

Hermes ships a partial ICU, so `Intl.PluralRules` has no data for most locales
and every count would select the `_other` form. The React Native SDK imports
`intl-pluralrules` from its own entry point, so this is handled for you as long
as you import the SDK before you initialize i18n. If you construct a
`Streami18n` in a module that loads earlier than the SDK, import the polyfill
first in your app's entry file:

```ts
import 'intl-pluralrules';
```

The runtime warns when the polyfill is missing for the active language rather
than failing silently.

## Discovering and type-checking keys

Four types, exported from both SDKs:

- **`TranslationDictionary`** — the one to reach for. Every SDK key, including
  the plural forms, and nothing else. A typo or a leftover 1.x key is a compile
  error. Extra plural categories (`_few`, `_many`, `_zero`) are accepted; a
  plural suffix on a key that is not plural is rejected.
- **`LooseTranslationDictionary`** — the same, plus any key you like, so one
  dictionary can carry your app's own copy. Nothing catches a stale SDK key
  here, so use it only where you actually need app keys. `registerTranslation()`
  and `translationsForLanguage` take `TranslationDictionary`, so a dictionary
  written inline at the call is checked:

  ```ts
  i18n.registerTranslation('de', {
    'participantList.muteAll.lable': 'Alle stummschalten', // ← compile error
  });

  const withOwnKeys: LooseTranslationDictionary = { 'myApp.thing': 'Hallo' };
  i18n.registerTranslation('de', withOwnKeys); // ← fine
  ```

- **`TranslationKey`** — the union `t()` accepts, where a plural appears as the
  bare key. Use it to type a `t` parameter; it is not the right key type for a
  dictionary.
- **`TranslationCatalog`** — every key mapped to its English copy. Type-only, so
  it adds nothing to your bundle: hover a key to see what it renders, or index
  it (`TranslationCatalog['participantList.muteAll.label']` is `'Mute all'`).

**A JSON catalog** is the file to hand a translator or a TMS. Neither SDK checks
one in — the copy lives inline at each `t()` call site, so a committed catalog
would be a second copy that goes stale. Generate it from a clone of the repo:

```bash
cd packages/react-sdk && yarn i18n:export
```

That writes `en.json` in the package root: 182 entries covering 180 keys, two of
which are plural pairs. The React Native SDK has the same script and produces 29
entries for 27 keys. Neither SDK ships formatter-expression keys today, so
nothing is held back from the export; the `--all` flag exists for when that
changes.

Keys are namespaced after the source tree, so they are predictable from the
component — `callControls.*`, `participantView.*`, `callStats.*`,
`callFeedback.*` — with genuinely shared copy under `common.*`. The last segment
is the modality: `.label`, `.ariaLabel`, `.placeholder`, `.title`,
`.description`, `.text`. Keys shared between the web and React Native SDKs use
identical strings (`common.live.label`,
`participantView.screenShare.stop.label`), so an app shipping both platforms
writes one dictionary.

### Keeping a language up to date across upgrades

When a later release adds a key, **your build stays green.**
`TranslationDictionary` is `Partial`, so nothing is required and the new string
renders its inline English until you translate it. That is deliberate — a
partial dictionary is always safe — but it does mean new copy arrives
untranslated without telling you.

To be told, diff your dictionary against the catalog at the type level. Declare
it `as const` so TypeScript keeps the literal keys, then `Exclude` them:

```ts
import type {
  TranslationCatalog,
  TranslationDictionary,
} from '@stream-io/video-react-sdk';

export const de = {
  'participantList.muteAll.label': 'Alle stummschalten',
  'common.cancel.label': 'Abbrechen',
} as const satisfies TranslationDictionary;

/** Every key still needing German. Hover it to read the list. */
type Untranslated = Exclude<keyof TranslationCatalog, keyof typeof de>;
```

`satisfies` is doing real work: it still checks every key against the catalog, so
a typo is an error, while `as const` preserves the literal keys that
`keyof typeof de` needs. A plain `: TranslationDictionary` annotation would widen
`keyof typeof de` to the whole catalog and the diff would always be empty.

Hovering `Untranslated` lists the missing keys, and it shrinks as you add them.
To turn "am I complete?" into a build failure — useful in CI after a version
bump — assert the diff is empty:

```ts
type AssertEmpty<T extends never> = T;
type TranslationsComplete = AssertEmpty<Untranslated>;
// ^ compile error naming a missing key until `de` covers the whole catalog
```

The catalog also carries six `relativeTime.*` entries (`Today`, `Yesterday`,
`{{ count }}d ago`, `{{ count }}w ago`) that come from the shared runtime rather
than from this SDK's call sites. No SDK component renders them; they are there so
an app calling `getDateString` or the `timestampFormatter` can translate them. If
your app does not, exclude them from the diff:

```ts
type Untranslated = Exclude<
  Exclude<keyof TranslationCatalog, `relativeTime.${string}`>,
  keyof typeof de
>;
```

Extra plural categories are safe in the diff: they are accepted by
`TranslationDictionary` but are not catalog keys, so they neither break the
`satisfies` check nor shrink the diff.

One caveat: there is no _runtime_ list of keys to diff against.
`TranslationCatalog` is a type, which is what keeps the typed surface free at
runtime, so this check is compile-time only. A script cannot ask the installed
package which keys exist — for that, generate the JSON catalog from a clone.

## App-owned keys

`useI18n().t` is typed to the SDK's catalog, so your own key is a compile error
there even though it resolves perfectly well at runtime — your dictionary is
registered on the same instance. The recommended pattern is one small hook that
widens `t`, so the place where key checking is given up is deliberate and
greppable. This is what `react-dogfood` does:

```ts
import { useI18n } from '@stream-io/video-react-sdk';
import type { TDateTimeParser } from '@stream-io/video-react-sdk';

export type AppTranslateFunction = (
  key: any,
  defaultValueOrOptions?: any,
  options?: any,
) => string;

export const useAppI18n = () =>
  useI18n() as { t: AppTranslateFunction; tDateTimeParser: TDateTimeParser };
```

The parameters are `any` deliberately. Under `strictFunctionTypes` a function
parameter is checked contravariantly, so the SDK's overloaded `t` — whose key
parameter is a union of _its_ catalog keys — is not assignable to one declared as
taking `string`.

Then import `useAppI18n` instead of `useI18n` in components that use app keys,
and keep `useI18n` where you are only rendering SDK copy. Type your app
dictionaries as `LooseTranslationDictionary`, and keep them in separate files
from your SDK dictionaries so the SDK ones stay strictly checked.

If you would rather keep key checking for your own copy too, run the same
generator the SDKs use. `@stream-io/i18n` exposes `generateI18nKeys` on its
`/codegen` subpath: point it at your source root and it produces a type-only
catalog of your `t()` call sites, which you can intersect with the SDK's
`TranslationCatalog` and derive your own dictionary types from. It is a
build-time, Node-only tool, so a `devDependency` is enough — do not take a
runtime dependency on `@stream-io/i18n`, because a second copy resolved from your
`node_modules` would register dayjs locales on the wrong module.

Keys resolved from a runtime value are the one case the generator cannot see.
Brand those with `asDynamicKey`, re-exported from both SDKs, and put their
English in a `runtimeDefaults` object layered under every language — that is the
`language.*` block in the `react-dogfood` example above.

## The full key map

[`i18n-2.0-key-map.json`](./i18n-2.0-key-map.json) is the complete mapping, hand
reviewed. Nothing regenerates it.

```json
{
  "react": {
    "count": 169,
    "newlyTranslatable": 11,
    "keys": {
      "Mute all": { "key": "participantList.muteAll.label" },
      "{{ direction }} fullscreen": {
        "split": [
          "participantView.actionsMenu.enterFullscreen.label",
          "participantView.actionsMenu.leaveFullscreen.label"
        ],
        "note": "…"
      },
      "Enter": { "note": "…absorbed; delete with no direct replacement." }
    },
    "added": [
      { "key": "ringingCall.callingState.joining.text", "copy": "Joining" }
    ]
  },
  "reactNative": { "count": 28, "newlyTranslatable": 0 }
}
```

Read it as:

- **`key`** — the straight rename. 165 of the 169 React rows and 27 of the 28
  React Native rows.
- **`split`** — one old key became two whole sentences. Two React rows, both the
  `{{ direction }}` menu pattern. Translate both new keys.
- **`mergedInto`** — this old key was absorbed as a plural form of another key
  and emits nothing of its own. One React Native row.
- **`note`** — read it. It records why a key landed where it did, or what has to
  change at the call site as well as in the dictionary.
- **A row with neither `key` nor `split`** — a sentence fragment with no
  replacement. Delete it. Two React rows: `Enter` and `Leave`.
- **`added`** — the 11 React keys that had no 1.x equivalent, because they were
  resolved from a runtime value and were never translatable: the eight
  `ringingCall.callingState.*` labels and the three `callStats.status.*`
  verdicts. New copy for you to translate, not a rename. React Native has none.
